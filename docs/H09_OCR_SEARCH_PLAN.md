# H09 / T12 encrypted source-linked OCR search plan

Status: proposed design only. No product code, schema change, build, inference, network operation, model installation, or acceptance claim accompanies this document. Implementation requires an independent pre-implementation security review of the concrete contracts below and the parent's assignment of a separate source unit. The H02 and N02 source phases remain separate.

## Original requirement and observed gap

`SOURCE_PROMPT.txt` H09 and its clarification at line 138 require attachment name/extension information search coupled to T12 OCR. They do not require every file format's body search or PDF/HWP editing. T12 at line 172 requires local processing and forbids automatic cloud fallback. `PRODUCT_SPEC.md` preserves these limits; `FEATURE_GAP_AUDIT.md` explicitly identifies the missing source attachment association. H09 and T12 remain partial with user acceptance unconfirmed in `FEATURES.json`.

Observed code paths:

- `AttachmentPanel.Ocr.cs` recognizes an explicitly selected attachment through a single-use authenticated `AttachmentReadLease`, bounded PNG preview decode, verified installed engine/models and a local child process. Its read-only result is revoked by source/selection/preview authority changes. `ApplyOcrResultAsync` currently calls `Workspace.ImportText("OCR 결과", text)` and saves a separate plain note; it stores no attachment identity or engine provenance. That behavior remains available as a distinct command.
- `NoteSearch.Find(EditingWorkspace, SearchOptions)` searches attachment `Name` only for `SearchField.Attachments`; `All` includes those names. Extension search works as literal matching within the name. The enumerable-only overload refuses attachment search because it has no owning workspace.
- `StoredAttachmentObject` is immutable by ObjectId and includes RootId, original Length/Sha256, wrapped key and authenticated chunks. `AttachmentObjectCodec.Decrypt` authenticates chunks and verifies the complete original SHA before returning plaintext. `SaveCoordinator.CreateAttachmentReadLease` checks note/version/session before and after authentication and binds a revocable keyless byte lease. A lease authorizes one read, not result publication.
- `SaveCoordinator.IsAttachmentPreviewCurrent` additionally checks the shared attachment preview epoch. The UI must still check exact selected entry and host lifetime; accepting a snapshot can revoke the epoch without changing an edit version.
- Current snapshot readers accept exactly schemas 1–10. `SnapshotSerialization.Options` currently uses the default options for schemas 9 and 10; simply adding a property would therefore change their historical bytes unless a new suppression resolver is introduced.
- `EditingWorkspace.Trash.PurgeTrash` removes selected note/current/history payloads and keeps contentless discarded causal witnesses. It preserves the retained attachment object collection. D11 already documents backups/previous/pending/object retention and does not promise secure erasure.

## Storage alternatives and selected first scope

| Choice | Consequence | First-unit assessment |
|---|---|---|
| Root-level per-object derivation collection | One recognized text for every note currently referencing the same immutable object; no note revision needed. Root merge, backup import, conflict/version policy, retention and global search changes require a new contract. Detach/purge can stop hits while derived text remains in the root alongside retained objects. | Useful later if the user explicitly chooses shared attachment OCR. Current-note apply would also change other referencing notes' search results unless the UI explained and authorized that effect. |
| Per-note metadata keyed by immutable object | Only the selected note gets OCR search text; no other note changes or acquires a hit. Existing note revision/history and selected-backup copy carry the metadata. A repeated object in another note requires that note's own explicit apply. | Recommended smallest bounded unit. It preserves the current command's selected-note authority and avoids introducing a root-global mutable derivation index. |

Choose a new immutable `NoteMetadata.AttachmentOcrResults` array, default empty, serialized only in payload schema 11. Each `StoredAttachmentOcrResult` records ObjectId, SourceSha256, exact recognized Text, TextSha256, and a bounded typed OcrProvenance. It is not inserted into Title/Text/StyledDocument, `StoredAttachmentObject`, an image block, or a generic note body. One stored result per ObjectId per note; no replacement/append-only history of multiple engines in the first unit. If the note already has a result for that object, refuse the new apply with a clear message. A separately reviewed replacement/removal command can follow; do not silently overwrite provenance.

The record has no signature, confidence guarantee, author attestation or arbitrary user-supplied provenance string. Vault authenticated encryption protects stored values against ciphertext tampering; it does not prove recognition correctness or that arbitrary imported metadata was produced by a particular executable. Imported authenticated records retain their recorded provenance as historical metadata rather than acquiring a new local-execution claim.

## Concrete proposed contracts

These APIs and types are proposals, not existing methods.

- `StoredAttachmentOcrResult(Guid ObjectId, string SourceSha256, string Text, string TextSha256, StoredOcrProvenance Provenance)` and `NoteMetadata.AttachmentOcrResults: ImmutableArray<StoredAttachmentOcrResult>`.
- `StoredOcrProvenance` contains bounded fixed engine/Leptonica/model commit identities, actual verified engine SHA256, fixed kor/eng traineddata SHA256 values, fixed language `kor+eng`, OEM=1, PSM=6, decoder/transform profile ID, source pixel width/height, recognized preview width/height and exact PPM input SHA256. The existing PpmOcrInput composites decoded straight BGRA over white with integer rounding `(channel * alpha + 255 * (255-alpha) + 127) / 255`; pin that policy in the transform profile along with nearest-neighbor preview mapping. Use a closed profile such as `png-preview-nearest-1024-v1` whose pixel/color/orientation policy is already the bounded decoder's policy. Do not describe this as recognition at original image resolution: the current preview can downsample large images and its prepared PPM already composites alpha over white; record the exact current transform rather than an unspecified alpha policy.
- `SaveCoordinator.CreateAttachmentOcrReadGrant(note, objectId, expectedVersion, expectedPreviewEpoch)` checks the current selected-note object/root and creates a genuine issuer-owned single-use registry entry and returns the existing lease plus a detached descriptor and keyless OcrGrantStamp. The stamp includes a fresh unpredictable coordinator-session nonce, grant GUID, original NoteId, captured EditVersion and AttachmentPreviewEpoch. The owner enforces a hard cap of four outstanding registry entries before authentication or allocation; pending, running and published entries count toward the cap. The registry entry binds all stamp fields, the exact immutable object/root/hash/length and lifecycle state. No public constructor can create an issued grant. A new coordinator/unlock creates a new session nonce; matching object bytes in a reopened vault do not revive an old grant. The grant descriptor includes ObjectId, RootId, SourceSha256 and original length, never a note/session/key/UI owner. The coordinator rechecks exact immutable object identity around authenticated decryption. The worker computes and compares source SHA from the actual authenticated borrowed byte span inside the lease's single `Consume`; it then decodes that same span. No second read or unverified file/name inference supplies the source hash.
- `InstalledOcrBackend.StartLinked(grant, models, token)` returns an operation with a keyless `OwnedOcrDerivation` result and actual `Settled` task. The owned result contains the authenticated detached descriptor, bounded UTF-8 result and provenance obtained from the same successful engine/model verification used to start this recognition, plus the exact prepared PPM hash and original grant stamp. All worker DTOs carry only bounded values, owned bytes and cancellation, never an issuer/coordinator/registry reference. Candidate construction is closed to the verified recognition path; no public Text+provenance constructor/factory or arbitrary result-deserialization API may mint a fresh trusted candidate. Stored imported metadata is not a candidate. Internal access from friend assemblies is a trusted-code convenience, not a cryptographic attestation boundary. Expose a trusted verified provenance DTO from `WindowsOcrBundle`; never synthesize an engine hash from a display label or accept a caller's model path as provenance. Preserve held verified-file handles through process settlement.
- `SaveCoordinator.ApplyAttachmentOcrResult(note, objectId, expectedVersion, expectedPreviewEpoch, OwnedOcrDerivation result)` is the only mutation bridge. It is owner-thread synchronous, single-use, checks current unlocked session/vault/root, exact active attachment identity/hash/length, note version and preview epoch before staging and again immediately before publication, and requires the original grant registry entry and stamp to match this current issuer/session, original NoteId, captured version/preview epoch and immutable source descriptor, and consumes the grant and owned result once. An object/hash match alone never authorizes A-to-B application, including identical objects shared by both notes. Every apply attempt atomically removes/consumes the issued entry before attempting publication; a failed mismatch or stale attempt also revokes the candidate and cannot be retried. The UI independently requires current host/selected entry/generation/token. The result is consumed or disposed on every failure path; workers never receive authority callbacks. The registry is independently revoked/cleared before public callbacks on lock, coordinator disposal, source edit/close, detach and any attachment preview epoch invalidation, including same-version snapshot acceptance. Owner-thread retirement also occurs on cancellation, selection change, host close, result disposal and StartLinked failure. A worker never calls a registry callback or holds the registry/issuer. Revocation marks an in-flight entry unusable immediately but does not free its accounted slot or owned buffers until the worker actually settles; ready/disposed entries retire through the owner path. These revocations prevent application immediately while running lease/process cleanup and global admission continue until actual settlement.
- `EditingWorkspace.ApplyAttachmentOcrResult` stages a complete candidate through the existing atomic note event/preflight path using Title/Text/Mode/Document/AttachmentIds unchanged and only the selected note's metadata extended. Validate schema 11, exact budgets and full candidate before changing any draft. The resulting selected note has a normal new revision/edit version; other notes and immutable objects are unchanged. Publish authoritative state before native/public observers. Observer errors after publication are reported as applied edited state rather than rollback.
- `EditingWorkspace.DescribeAttachmentOcrResults(note)` provides only the current note's records whose ObjectIds are in its current AttachmentIds. `NoteSearch.Find(workspace, options)` matches name OR linked OCR text using the existing literal normalization/ordinal-ignore-case policy for `Attachments` and `All`; Title and Body remain unchanged. Empty query/view/folder/tag/sort behavior remains as today. No OCR text is copied into saved-search configuration, recent-note title, OS index, logs, lock-screen notifications, telemetry, or plaintext cache. Search does not decrypt new attachment bytes or trigger recognition.

## Budgets, validation and ownership

Before allocation or JSON expansion, validate closed profiles, all scalar/string lengths, record count and source relations. Initial limits: at most 16 records per note (the current attachment-reference cap), one record per ObjectId in that note; at most 128 serialized record occurrences across retained current notes and history; at most 262,144 UTF-8 bytes and 65,536 UTF-16 code units per result; at most 1 MiB aggregate retained OCR UTF-8 text across current/history occurrences. Repeated historical copies count toward both limits rather than being hidden by deduplication. Empty OCR text is not eligible for linked apply. Enforce existing complete 16 MiB encrypted vault file/payload limits without enlarging them, including all JSON escaping and provenance bytes. Reject the whole candidate on any budget failure, leaving existing state and ciphertext intact.

Require well-formed Unicode, no NUL, and strict UTF-8; preserve the exact recognized output and its line endings. Hash exact UTF-8 bytes for TextSha256; never normalize text to compute its provenance digest. Search normalization remains an ephemeral matching operation. Each record's SourceSha256 must equal its referenced immutable object's recorded canonical lowercase SHA, and ObjectId must be in that current note/revision's AttachmentIds. Root identity follows the authenticated snapshot's attachment root, not a separately editable user field. Check source content again during genuine recognition, not by trusting the stored descriptor alone. The first runtime profile accepts only the backend's verified fixed engine/models and existing supported PNG decoding; arbitrary image/file body parsing is outside this unit.

Owned UTF-8 output/result bytes, PPM/source/raster scratch and disposable candidates are zeroed at the end of their owned lifetime, including allocation observers, exceptions, cancellation and process teardown. Fixed/growth buffer bounds apply before every write; replaced owned buffers must be cleared. No borrowed attachment or caller buffer is changed. Stored/search/UI .NET strings and native/OS copies cannot be reliably zeroed; lock closes/revokes drafts, clears OCR display, releases key owners immediately and removes string references. Do not claim secure erasure of GC strings, process/OS/native copies or previous encrypted files.

Existing process limits remain: PNG source max 4 MiB, bounded preview at most 1024 per axis/1,048,576 pixels, PPM cap, 20-second bounded process waiting policy, stdout 262,144 bytes, stderr 4,096 bytes and thread cap. Cancellation does not prove native/process immediate termination. Hold application image/OCR admission until the operation actually settles; stale results never publish or apply. Result preview authority survives only while the exact source remains current, and is revoked before native setters run. Linked apply and encrypted save need their own post-recognition source checks; completing recognition is not authority to mutate later.

## User flow and save behavior

Keep current explicit local model installation/selection and recognize buttons, read-only preview and “OCR 결과를 새 메모로” behavior. Add a distinct “OCR 결과를 이 첨부의 검색에 연결” button. Explain that only this note's selected attachment search metadata changes; the original body and image are preserved, recognition may be wrong, and another note sharing the object does not automatically gain OCR search text. No automatic recognition on paste, attachment load, search, startup, unlock or model installation.

Capture exact source authority before recognition; invalidate result on edits, same-version snapshot acceptance, selection/detach, host close, lock and cancel. Before explicit linked apply revalidate all authority. After successful metadata application use existing whole dirty save. Save/flush failure reports retained unsaved edited metadata; it cannot promise rollback after an applied event. No hidden import-new-note fallback occurs when linked apply fails. Result clearing/notice/native enable changes can reenter; recheck authority after each native boundary and never keep an old allowed closure alive after revocation.

## Schema 11 and compatibility inventory

A schema change is necessary because schemas 1–10 never promised preservation of this new field. No metadata is injected into legacy text, document SourceJson, attachment name/MIME, encrypted chunk contents or an opaque node to avoid versioning.

Before implementation, enumerate every exact schema allowlist in SnapshotValidation, AttachmentEnvelope envelope2 pairing, EncryptedVault root-key transfer/seal/save/read/hidden recovery/downgrade checks, EditingWorkspace Capture/AcceptPrepared, backup preview/selected import, and recovery paths. Add 11 only where it represents the same root-encrypted envelope with new validated note metadata. Unsupported future 12+ is refused before decrypt/apply where existing framing permits; do not turn exact lists into unbounded `>=5` acceptance. Introduce sticky OCR-schema state and reject all downgrade writes after loaded/prepared/hidden schema11, including empty arrays.

Add a resolver preserving the exact schemas 9 and 10 JSON while omitting OCR fields in every schema 1–10. Older schemas must refuse nonempty hidden OCR metadata instead of silently dropping it. New schema11 validates OCR arrays on both current notes and every historical revision. Preserve canonical rich v1, opaque unknown document content and canonical rich v2 authenticated image references byte-for-byte; neither the OCR bridge nor the search predicate parses or rewrites document SourceJson. Maintain H01 refs/root validation and schemas1–10 test vectors exactly.

Whole encrypted backups preserve complete schema11 note/history metadata and original objects. Selected backup import copies only selected note metadata with the exact referenced immutable objects, revalidates the current authenticated root and immutable-object equality, advances the candidate to 11 when needed, and applies the same budgets. New note IDs from selected backup copies do not change ObjectId/SourceSha/text/provenance. History restore restores OCR metadata together with that revision's attachment references. Existing histories never receive retrospectively inserted records. Any future sync/Android writer must understand/preserve 11 or refuse it; do not promise a currently absent merge algorithm's behavior.

## Attach/detach and D11 retention

Applying OCR only to note A does not change note B even when they share ObjectId. Adding the same object to another note does not inherit A's result. Detaching an object from A removes its active OCR metadata in the same validated note event; previous revision metadata and the original object remain retained. Restoring the old revision can restore both reference and OCR metadata. This is a search-scope change, not cryptographic object deletion.

Normal trash remains a view filter: active search excludes deleted notes, explicit Trash/All can match their current linked metadata while unlocked. D11's successful backed-up purge removes the selected note/current/history and their per-note OCR metadata from the new current snapshot; causal `StoredDiscardedRevision` witnesses remain contentless and gain no OCR fields. It does not collect retained attachment objects, erase the recognizable source image, remove OCR metadata from backups/previous/pending snapshots, or securely erase freed strings. All retained other-note records remain. Restoring a purged old backup must still respect discarded causal witnesses and cannot silently resurrect the purged note/derivation. No new retention or GC policy is introduced by this unit.

## Independent pre-implementation security gate

This plan is ready for a separate reviewer; no independent review is claimed here. Review must settle: per-note scope versus shared-object expectations; authenticity of source/PPM/provenance handoff; lack of forged proof claims; issuer-owned single-use grant registry, original note/session stamp and A-to-B/reopened-session replay refusal, closed trusted candidate construction and all same-version/native boundaries; exact11/legacy serialization and hidden downgrade behavior; full payload and historical duplication budgets; detach/restore/import/D11 causal retention; immediate key release versus delayed worker ownership; and search/display clearing on lock. Record findings and resolutions separately from the implementer's self-review. Only after the parent accepts that review and assigns the first concrete unit may schema/storage or UI implementation begin.
