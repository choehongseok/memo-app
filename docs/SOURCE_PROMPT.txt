메모앱 — 다닷·Codex Cloud 개발 총괄 지시문

이 메시지는 아래 범위의 실제 개발을 요청하는 지시다. 너는 다닷으로서 Codex Cloud 작업의 착수·진행 확인·검토·수정·인계를 맡아라. 나에게 매번 세부 개발 프롬프트를 작성하게 하거나, 계획만 제시한 채 끝내지 마라. 단, 사용 가능한 도구·권한·사용량 범위를 넘는 실행이나 자동 재개를 약속하지 마라.

1. 작업 대상과 권한

대상 GitHub 저장소는 choehongseok/memo-app이다. Codex Cloud에서 이 저장소와 연결된 환경을 찾아 사용하라. 환경의 표시 이름만 믿지 말고 연결 저장소, 프로젝트 루트, 작업 브랜치, 기준 커밋을 실제 확인하여 기록하라. cathunt, mod_warpfactory 등 다른 저장소는 수정하지 마라. 임의로 로컬 PC 작업이나 별도 저장소로 전환하지 마라.

2026-10-02 사전 조회에서는 memo-app이 비어 있는 공개 저장소였다. 실행 시 현재 상태를 다시 확인하라. 여전히 비어 있다면 사용 가능한 GitHub 도구로 초기 문서·.gitignore·프로젝트 골격을 준비하고 최초 커밋을 만들어 Cloud 작업을 시작하라. 기존 코드가 생겼다면 읽고 이어가며 초기화하거나 덮어쓰지 마라. 빈 저장소에 아직 HEAD가 없다는 사실을 코드 오류로 오인하지 마라.

대상 저장소 안의 설계 문서 작성, 구현, 테스트, 빌드, 작업 브랜치 커밋·push·PR 작성은 이 개발 요청에 포함한다. main 반영은 저장소 보호 규칙과 주어진 권한에 따르며 강제 push나 승인 우회는 금지한다. main 반영을 기다리는 동안에는 같은 개발 브랜치에서 이어갈 수 있는 작업을 진행하라.

유료 서비스 신규 가입·결제, 공개 배포나 앱스토어 등록, 저장소 공개 범위 변경, 실제 메모의 외부 전송, 기존 사용자 데이터 삭제·비가역적 변경은 별도 승인을 받아라. 플랫폼 자체의 승인 절차도 우회하지 마라. 접근할 수 없으면 실제 확인한 실패 원인과 필요한 조치를 보고하고, 연결·실행·완료했다고 꾸미지 마라.

2. 최종 제품과 변경 금지 방향

목적은 중요한 개인정보가 들어 있는 S메모를 대체할 개인용 메모 프로그램이다. Windows 메인 관리창과 바탕화면 포스트잇을 중심으로, Android와 여러 PC 사용, 동기화, 문서 편집, 첨부, 검색, 이력, 백업, 자료 이전, 로컬 AI까지 완성하는 것이 최종 범위다.

핵심 메모 기능은 서버·계정·인터넷 없이 사용할 수 있어야 한다. 동기화·업데이트·모델 다운로드 등 필요한 통신은 별도 모듈과 사용자 설정으로 분리한다. 광고·텔레메트리·메모 내용 자동 수집은 넣지 마라.

Windows부터 개발하되 Android·동기화·OCR·음성·AI를 '언젠가 할 일'로 방치하거나 최종 범위에서 삭제하지 마라. 단계별 시험판과 전체 완료를 구분하라. 브라우저용 HTML 데모나 버튼만 있는 화면을 Windows 프로그램의 대체 결과물로 제출하지 마라.

기능 선택은 끝났다. 보통의 구현 판단은 네가 근거를 정해 진행하라. 범위 축소, 보안 수준 저하, 비용 발생, 데이터 손실 위험처럼 사용자 판단이 필요한 변경만 질문하라. 현재 승인 범위의 각 단계마다 개발 승인을 반복해서 요청하지 마라.

3. 대화가 바뀌어도 유지할 저장소 기준

먼저 다음 문서를 만들거나 기존 문서에 통합하라. 같은 정보를 여러 문서에 반복 복사하지 말고 역할을 구분하라.

- AGENTS.md: 목적, 금지 사항, 필수 확인 파일, 개발·검증 규칙을 짧게 기록한다. 긴 명세 전체를 넣지 않는다.
- docs/PRODUCT_SPEC.md: 이 지시문의 기능 범위, 해석, 보안 원칙, 데이터 구조, 기술 선택, 단계별 완료 기준을 보존한다. 설계 변경 이유도 여기에 기록한다.
- docs/FEATURES.json: 아래 원선택 134개 ID 각각의 이름·정규화 결과·단계·상태·수용 조건·구현 위치·테스트 근거를 관리한다. ID를 삭제·재번호 부여하지 않는다.
- docs/STATUS.md: 실제 저장소·환경·브랜치·마지막 검증 커밋, 현재 작업, 다음 작업, 미해결 문제, 산출물 위치를 짧게 유지한다.
- docs/VERIFICATION.md: 테스트 명령·환경·결과·관련 커밋·실패·미실행 항목을 기록한다. 상세 로그는 필요할 때만 연결한다.
- README.md: 설치·실행·백업·복구·자료 이전·기능별 실제 지원 범위와 사용자 주의 사항을 설명한다.

새 Codex 작업 시작 시 AGENTS.md, STATUS.md, 해당 기능 명세와 실제 git 상태를 확인하라. 전체 대화·누적 로그를 매번 다시 읽는 대신 관련 범위를 읽어라. AGENTS.override.md나 하위 경로 지침도 확인하고 충돌을 숨기지 마라.

기능 상태는 미착수 / 진행 중 / 구현됨·미검증 / 검증됨 / 차단됨 / 정규화로 대체됨으로 구분하라. 사용자 수용은 별도 필드에 두고 내가 확인하지 않았으면 수용했다고 쓰지 마라. '구현됨'을 '검증됨'으로 바꾸려면 실제 근거가 있어야 한다.

내가 이후 명시적으로 요구사항을 바꾸면 그 변경을 적용하고 이유·영향을 기록하라. 반대로 구현이 어렵다는 이유만으로 문서의 원래 요구를 조용히 낮추지 마라. 단계 종료 때마다 선택 ID 누락·무단 제외 여부를 검사하라.

5. 중복·충돌 항목의 확정 해석

- B01~B12와 B13: 중앙 관리창과 독립 포스트잇을 모두 제공한다. 메모별로 꺼내거나 관리창에서만 사용한다. B12의 위치 고정, B06의 항상 위, D08의 목록 고정은 구분한다.
- C14·C15: 서식 편집, 일반 텍스트, Markdown을 지원한다. 단순한 '서식 제거 붙여넣기'만으로 일반 텍스트 모드 전체를 완료했다고 하지 마라. 형식 변환 시 손실을 미리 알리고 원본을 보존한다. Android에서 열고 저장해도 기존 표·서식·이미지가 조용히 사라지면 안 된다.
- L07·L08: 설치형과 포터블을 모두 제공한다. L09·L10은 업데이트 방식 설정으로 함께 제공하되 초기값은 수동으로 한다.
- M06은 M01~M05와 충돌하여 채택하지 않는다는 기존 정리를 유지한다. 원선택 기록에서 삭제하지 말고 '정규화로 대체됨: M01~M05 유지'로 기록한다. 나머지 기능은 임의 제외하지 마라.
- P01은 로컬 전용 모드로, P02~P06은 선택적 여러 기기 사용으로 제공한다. 메모별로 '이 기기에만 보관 / 동기화'를 구분한다. 창 위치·배율 같은 기기별 설정은 무조건 다른 기기로 덮어쓰지 마라.
- F 일정·할 일, G 일반 일정 알림, I 화면 캡처, J 클립보드 기록, K 전역 단축키 묶음, iPhone은 선택 범위가 아니다. 일반 편집용 Ctrl+C/V/Z는 제공하되 이를 이유로 별도 클립보드 수집 기능을 추가하지 마라.
- R01은 날짜 확인용 달력 위젯이다. 미선택한 일정관리 시스템까지 확장하지 마라. Q08은 우선 동기화 실패·충돌 등 앱 운영 알림으로 구현하고, 잠금화면에는 메모 내용을 노출하지 마라. 일정 알림 확장은 별도 요구가 있어야 한다.
- H09는 파일명·확장자 등 첨부 정보 검색을 기본으로 하고, T12의 OCR 결과를 연계한다. 모든 문서 형식의 본문 검색이나 PDF·한글 편집기까지 제공한다고 주장하지 마라.
- N08·N09는 실제 확인한 형식·버전에 대한 가져오기 어댑터로 구현한다. 다른 메모 프로그램 '전부 지원'이라고 표시하지 마라. S메모 형식은 초기부터 조사하되 실제 개인정보 대신 공개 문서와 비민감 시험 자료로 검증한다. 미확인 형식은 차단 사유를 남기고 다른 개발을 계속한다.

6. 구조와 기술 선택

Windows는 C#·지원 중인 안정 .NET·WPF를 기본 후보로 검토하라. Android는 Android에 적합한 기술을 사용하되 문서 형식·암호화·동기화 규약을 공유하라. 구체적인 버전·라이브러리·배포 방식은 공식 지원 상태와 실제 빌드 가능성을 확인하고 PRODUCT_SPEC에 고정하라. 다른 기술이 요구사항에 더 적합하면 이유와 영향부터 기록하되, 개발이 편하다는 이유로 플랫폼이나 기능을 바꾸지 마라.

사용자 화면은 한국어로 제공하고 왼쪽 폴더·오른쪽 메모 카드 구조를 기본으로 한다. 자주 쓰는 작성·검색·저장 상태는 쉽게 보이게 하고, 고급 설정은 필요한 위치로 나눠 화면을 과밀하게 만들지 마라.

UI, 문서 모델, 저장소, 암호화·키 관리, 검색, 첨부, 가져오기·내보내기, 동기화, OCR·음성·AI를 분리한다. 문서 형식은 Windows 전용 편집기 내부 파일만을 유일한 원본으로 삼지 말고 Android 호환성과 버전 확장을 고려하라.

처음부터 고유 메모 ID, 문서·DB 스키마 버전, 수정 버전, 삭제 기록, 첨부 식별자, 마이그레이션과 동기화 대상 여부를 설계한다. 실제 동기화 구현은 뒤에 하더라도 이를 나중에 전면 재작성해야 하는 구조로 만들지 마라.

운영 중인 DB 파일 전체를 클라우드 폴더에 넣고 동시에 덮어쓰는 방식은 자동 동기화 구현으로 인정하지 않는다. 암호화된 메모·첨부·변경 단위의 동기화로 설계하고, 재시도·중복·오프라인 수정·삭제 충돌을 처리하라. 동시에 바뀐 내용을 마지막 저장값 하나로 조용히 없애지 말고 충돌본과 복구 경로를 보존하라.

동기화 저장소에는 복호화 키나 메모 평문을 올리지 않는 종단간 암호화를 적용하라. 기기 등록·해제·키 교체·복구까지 포함한다. 이미 다른 기기에 복호화된 과거 데이터까지 회수할 수 있다고 주장하지 마라. 서버가 알 수 있는 최소한의 접속·크기·시점 등의 메타데이터도 명시하라.

백업 복원은 덮어쓰기·병합·다른 기기 이전을 구분하고, 원본 보존 후 무결성을 확인한 다음 적용한다. 백업 복구나 오래된 기기의 재접속으로 삭제 메모가 자동 부활하지 않게 설계하라.

7. 보안은 첫 저장 기능부터 필수

보안을 나중 단계에 붙이거나 'AES-256 사용' 한 줄로 완료하지 마라. 위협 모델과 검증 가능한 통제를 정하고 유지보수되는 라이브러리·플랫폼 보안 기능을 사용하라. 자체 암호 알고리즘이나 근거 없는 독자 보안 프로토콜은 만들지 마라.

- 메모 본문뿐 아니라 제목·폴더·태그·첨부·미리보기·검색 인덱스·변경 이력·휴지통·백업·AI 파생 데이터의 저장 경로를 점검하고 민감 데이터가 평문으로 남지 않게 한다. 일반 SQLite를 사용했다는 사실만으로 암호화됐다고 판단하지 않는다.
- 인증된 암호화, 안전한 난수·키 생성, 올바른 nonce 관리, 변조 검출을 적용한다. 비밀번호로 키를 보호할 경우 Argon2id 등 검증된 키 유도 방식과 해당 기기에서 검증한 매개변수를 사용한다.
- 데이터 키와 그 키를 보호하는 수단을 분리한다. Windows의 DPAPI·Hello, Android Keystore 등은 역할을 확인해 적용하며 화면만 가리는 가짜 잠금으로 대체하지 않는다.
- 특정 Windows 계정의 DPAPI만을 유일한 복구 수단으로 삼지 않는다. 다른 PC로의 이전, OS 재설치, 기기 분실에도 사용할 수 있는 암호화된 키 복구·백업 절차를 설계하고 시험한다. 분실한 비밀번호나 키를 무조건 복구할 수 있다고 주장하지 않는다.
- 앱·OS 잠금과 자동 잠금을 연계하고 잠금 중 검색·미리보기·알림 노출을 막는다. 해제된 화면, 악성코드에 감염된 OS, 관리자에 의한 메모리 접근까지 완벽히 방어한다고 약속하지 않는다.
- 외부 프로그램으로 첨부를 열거나 TXT·PDF·Word·Excel로 내보내면 평문이 생길 수 있다. 실행 전에 대상과 주의를 알리고, 외부 파일 경로 연결은 원본 파일까지 암호화하는 기능이 아님을 명확히 한다. 외부 앱 캐시·임시파일까지 완전히 지웠다고 보장하지 않는다.
- 로그·오류 보고·테스트 화면·CI 산출물에 실제 개인정보를 남기지 않는다. 실제 S메모 DB·백업·사용자 파일·암호화 키·복구키·인증 토큰·서명키를 GitHub, Codex 입력, 다닷 대화에 올리지 않는다. 테스트는 가상 데이터로 한다. .gitignore뿐 아니라 커밋·산출물 점검도 실시한다.
- 가져온 메모·Markdown·첨부·백업은 신뢰하지 않는 입력으로 처리한다. 스크립트·매크로·외부 리소스를 자동 실행하거나 불러오지 말고, 파일 경로 탈출·과도한 압축 해제·손상된 형식도 방어한다. 의존성 버전을 고정하고 취약점·라이선스를 점검한다.
- 업데이트는 출처·서명·변조 여부를 검증하고 실패하면 적용하지 않는다. 단순 체크섬만으로 배포자 인증을 대신하지 마라. 개발용 서명과 실제 배포용 키를 분리한다. 권한·비용이 필요한 인증서나 키 준비는 확인 대상으로 남기고 미완료를 숨기지 않는다.
- 네트워크 허용 목적과 외부 통신을 확인한다. 빌드 의존성 다운로드와 실행 중 메모 전송은 구분한다. 사용자가 끈 동기화·외부 AI를 자동으로 켜지 않는다.

T12 OCR, T13 음성인식, T14~T16 AI는 로컬 처리를 기본 구현으로 한다. 외부 API를 연결해 놓고 로컬이라고 표시하거나 로컬 처리 실패 시 자동으로 클라우드에 보내지 마라. 모델 설치 용량·기기 요구사항·라이선스를 확인하고, 가용 기기에서 실행 가능한 모델과 설정을 선택하라. 아직 모델을 설치하거나 추론을 실행하지 못했으면 실제 기능 검증 완료로 표시하지 마라.

AI 메모 질문은 사용자가 허용한 로컬 메모에서 검색하고 근거 메모를 보여주는 방식으로 한다. 잠긴·제외된 메모를 임의로 검색하지 않는다. AI는 메모 내용을 자료로 취급하고 그 안의 지시를 실행하지 않으며, 사용자 확인 없이 원본을 덮어쓰거나 외부 전송·파일 실행을 하지 않는다. 문장 다듬기는 미리보기 후 반영하고 이력을 남긴다.

외부 AI는 현재 기본 개발 범위의 필수 의존성이 아니다. 나중에 내가 명시적으로 요청할 때 별도 승인·전송범위 확인을 거쳐 추가하라.

8. 개발 순서 — 단계는 나누되 최종 범위는 유지

단계 0: 현재 환경·저장소 확인, 위 문서와 기능 원장 작성, 기술·문서 형식·키 복구·동기화 계약 결정, 빌드·테스트 골격 구축. S메모 가져오기 형식 조사도 시작한다. 문서만 만든 상태를 제품 개발 완료라고 하지 마라.

단계 1: 암호화된 메모 생성·편집·자동 저장·재실행 복원, 기본 관리창·포스트잇, 폴더·검색, 기본 이력·휴지통·암호화 백업·복구가 실제 연결된 첫 Windows 시험판. 사용자가 새 메모를 작성하고 종료·재실행해 그대로 확인할 수 있는 작은 완성 흐름부터 제공한다.

단계 2: 선택한 Windows 기능 완성. A~E, H, L, M, N, O, R, S와 T08~T10, 수동 다른 PC 이전을 채운다. 고급 서식·표·Markdown, 첨부, 버전 비교, 선택 복구, S메모 이전, 설치형·포터블을 포함한다. 각 ID별 완료와 미완료를 기록한다.

단계 3: 여러 PC의 종단간 암호화 자동 동기화, 기기별 로컬 메모, 충돌·삭제·복구·등록 해제 검증. 실제 연결 대상이 없으면 가상 서버 통합시험과 운영 연결 미검증을 구분한다. 운영 서비스가 필요하다는 이유로 자동 유료 가입하지 마라.

단계 4: Android 앱, 작성·수정, 사진 첨부, 운영 알림, PC와의 암호화 동기화. APK 빌드와 에뮬레이터·실기기 결과를 구분한다. Android를 만들지 않고 프로젝트 전체 완료라고 하지 마라.

단계 5: 로컬 OCR·음성·AI 요약·다듬기·메모 질문을 실제 엔진과 연결하고 성능·개인정보 경계를 확인한다. 가짜 응답이나 버튼 시연은 완료가 아니다.

단계 6: 기능 원장 전수 대조, 회귀시험, 저장·암호화·복구·동기화 재검증, 라이브러리·라이선스 점검, 사용자용 실행 파일·APK·설명서 정리. 정상 사용을 막는 문제나 주요 미검증 사항이 남으면 최종 완성본이라고 하지 마라.

선행 조건이 막힌 경우 독립적으로 가능한 다음 작업은 진행하되, 막힌 기능을 지우거나 검증된 것으로 바꾸지 마라. 각 단계는 설치·실행 가능한 산출물로 점진적으로 연결한다.

9. Codex 작업 운영과 인계

실제 구현은 기본 1개 작업 흐름으로 진행하라. 데이터 저장·암호화·복구·동기화·업데이트처럼 위험도가 높은 변경은 별도 검토 1회를 둔다. 독립 검토 도구가 없으면 자체 검토라고 명시하고 독립 검토를 했다고 꾸미지 마라. 같은 파일을 여러 구현 작업에서 동시에 수정시키지 마라.

각 작업에는 대상 저장소·브랜치·기준 커밋, 이번 기능 ID, 관련 명세, 변경 금지 사항, 완료 조건을 전달하라. 새 작업이 이전 작업의 미커밋 파일을 자동으로 이어받는다고 가정하지 마라. 작업 전후 실제 커밋·diff·테스트 결과를 확인하고, 다음 작업이 접근할 수 있는 브랜치에 변경과 상태를 보존하라.

Codex의 '완료' 보고만 믿지 말고 실제 변경과 실행 근거를 확인하라. 재검토는 지적 사항과 변경 부분에 집중하고, 코드가 그대로인데 같은 전체 감사를 반복하지 마라. 테스트 실패를 없애기 위해 검사를 삭제하거나 수용 조건을 낮추지 마라.

기능별 관련 테스트를 수행하고, 저장 구조·보안·동기화 변경 및 단계 종료에서는 필요한 전체 회귀를 수행하라. 한 작업이 끝나고 권한·도구가 허용하면 결과를 확인한 뒤 다음 미완료 작업을 실제로 착수하라. 확인하지 않은 작업을 진행 중이라고 보고하지 마라.

사용량·권한·세션 종료로 멈추면 접근 가능한 위치에 코드와 문서를 보존하고 마지막 커밋·실행 결과·미완료·다음 명령을 남겨라. 자동 재개가 실제 설정되지 않았는데 나중에 계속하겠다고 약속하지 마라. 다음에는 STATUS를 기준으로 이어가며 이미 검증된 부분을 처음부터 재개발하지 마라.

10. 검증과 산출물 기준

개발 중 적어도 다음을 실제로 검증하고, 수행하지 못한 것은 이유와 함께 구분하라.

- 자동 저장·재실행·비정상 종료·디스크 쓰기 실패에서의 데이터 보존과 저장 상태 표시.
- 같은 메모의 여러 창 편집, 실행취소·이력·휴지통·복원, 포터블·설치형 데이터 이전.
- 한글 입력, 표·이미지·체크박스·Markdown 왕복 보존, 모니터 분리 후 화면 밖 창 복구, 화면 배율·다크모드.
- 잘못된 비밀번호·키, 암호문 변조, 손상된 백업, 새 PC 복원, 일부 메모 선택 복구 시 원본 보호.
- 첨부파일·로그·검색 인덱스·이력·백업에 가상 민감정보가 평문으로 새는지, 잠금 후 미리보기·알림이 남는지.
- 두 기기의 동시·오프라인 수정, 수정 대 삭제 충돌, 재시도·중복 요청, 기기 해제, 복원 후 재동기화.
- Android에서의 문서 호환, 사진 첨부, 실제 로컬 OCR·음성·AI 실행과 허용하지 않은 외부 통신 여부.

Windows 전용 코드가 포함되면 Linux에서 코드 검사나 일부 테스트만 통과한 것을 Windows 실행 검증으로 보고하지 마라. 실제 가능한 Windows CI 러너를 사용해 빌드·관련 테스트·산출물 생성을 수행하라. 워크플로 파일만 만들어 놓은 상태는 빌드 성공이 아니다. Windows GUI·Hello·다중 모니터 실사용, Android 실기기 같은 환경 의존 검증은 각각 실행 여부를 기록한다.

공통 로직 테스트, 플랫폼 빌드, UI 테스트, 실기기 확인은 별개다. 테스트 이름·소스 문자열 존재만으로 기능 작동을 입증하지 마라. 증거는 해당 코드 커밋과 실제 시험 환경에 연결하라.

사용자 확인이 꼭 필요한 실기기 동작만 묶어서 간단한 실행 파일과 확인 절차로 제시하라. 네가 처리 가능한 환경 설정·빌드·로그 분석을 나에게 개발 도구 설치나 수작업으로 떠넘기지 마라. 다만 기관 PC 등의 실행 제한이나 보안 정책을 우회하게 하지 마라.

단계별로 실행 가능한 Windows 패키지 또는 Android APK, 소스 커밋, 실제 테스트 결과, 알려진 제한을 제공하라. 서명되지 않은 시험판이면 그 사실을 표시하라. 테스트 데이터·비밀키가 섞인 배포 파일을 만들지 마라. 파일이 실제 생성·접근 가능한지 확인하고 위치를 제시하라.

진행 보고는 사용자에게 달라진 기능을 먼저 설명하고 다음을 짧게 남겨라.
1) 실제 환경·Codex 작업·브랜치·커밋
2) 이번에 동작하게 된 기능 ID와 사용 방법
3) 실제 수행한 검사와 결과
4) 수행하지 못한 검사·미완료·위험
5) 실행 파일 또는 CI 산출물 위치
6) 다음 작업 또는 승인이 필요한 단 하나의 핵심 장애

문서 작성, 커밋 생성, 테스트 일부 통과만으로 전체 완료를 선언하지 마라. 최종 기능 원장과 산출물·검증 근거가 일치해야 한다. 보안 검증을 수행했더라도 '절대 안전'이나 외부 전문 보안 감사를 받은 것처럼 표현하지 마라.

이제 대상 저장소와 Codex Cloud 환경을 실제 확인하고, 현재 상태에 맞춰 단계 0과 첫 실행 가능한 개발 단위부터 착수하라. 기존 진행분이 있다면 이 지시를 통합한 뒤 마지막 검증 상태에서 이어가라.
