# Bounded encrypted attachment storage proposal

## Purpose and preserved scope
Continue H01-H09 and the original134 requirements using synthetic files only. Preserve original file bytes, encrypted names/MIME/length/hashes, immutable note/history references, exact old ciphertext on migration failure, and a genuinely self-contained backup. No automatic external file opening, network fetch, account, permissions, installer or real personal data. This is a proposal pending independent storage/security review, not implemented functionality.

## Options and recommendation
1. Recommended first vertical unit: immutable encrypted object/chunk records inside the bounded encrypted snapshot. Per-object random data keys and authenticated chunks remain separate logical objects, while existing atomic one-file save/backup/recovery carries every referenced object. Base64 ciphertext overhead reduces usable attachment capacity and autosave rewrites the container; this is an explicit trial limit, not final scope reduction.
2. Later physical object files: better large-file/incremental sync behavior, but requires atomic manifest/object coordination, orphan retention, sidecar-aware recovery and a new full-backup container. Do not introduce missing-object backups as a shortcut.

Trial bounds: original file4MiB; total retained attachment plaintext8MiB (including history/trash and retained unreferenced records); object count128; per-note active references16; chunk64KiB; existing entire envelope16MiB still applies. Full byte/history/ref preflight must reject the whole operation before publishing and preserve all old state. Keep ciphertext objects needed by any immutable history/trash reference; no automatic permanent deletion.

## Key lifetime and envelope proposal
Current EncryptedVault creates a fresh snapshot wrapping key each process and VaultEnvelope.Decrypt deliberately zeroes the recovered old key. Wrapping persistent attachment keys with that ephemeral key alone would lose attachments on restart. Preserve that freshness policy instead of silently changing it.

Propose explicit envelope2 with one additional authenticated key package containing a random attachment-root identifier and32-byte random attachment root key. Wrap that package with the current fresh snapshot wrapping key using a separate fixed AAD domain. The existing recovery-secret package unwraps that snapshot key; plaintext snapshot itself never contains key bytes. Keep envelope1 reading and exact original previous/failure bytes; strict version/layout/AAD and key ownership/zeroing must be reviewed before implementation. Envelope2 keeps the84-byte header with explicit version2, followed by recovery wrap32, snapshot-DEK wrap32, root packet wrap48, then payload. Root packet plaintext is rootUUID16 big-endian || rootKey32. AES-GCM package nonce12 CSPRNG/tag16; AAD is the complete header plus purposes1/2/4/3. Exact overhead308bytes, checked lengths and EOF; envelope1 pairs only schema1-4, envelope2 only schema5. Reserve3 wrapping uses per preparation attempt, including failures/retries, and refuse before exceeding2^20. Old clients reject envelope2 without writing.

Attachment root identity is an authenticated non-secret snapshot field and must match the encrypted key package. Keys live only in the EncryptedVault owner and are included in explicit key release/zeroing, never NoteDraft/Workspace/UI/history/hidden-plaintext/PreparedSnapshot or logs. Decrypt-to-Open uses explicit single ownership transfer/clone then finally-zero of temporary root and old snapshot key; inspection/import paths also dispose/zero root material. Existing nonempty root identity cannot rotate or mix roots in this unit.

Before encrypting any attachment, successfully anchor the new root by committed current envelope2 bytes with matching current ciphertext fingerprint; Prepare, flush or pending bytes alone do not anchor it. If that first anchor fails, do not create object ciphertext or attachment references. This is necessary because a plaintext-hidden recovery after failed preparation must not depend on a root key that was never persisted and is zeroed at lock. An already anchored root stays recoverable from the original current/previous candidate after subsequent write faults.

## Object format and nonce proposal
Each imported object gets a fresh UUID and32-byte random data key. Immutable IDs may be shared by duplicate notes/revisions, but never reused to encrypt different content. Derive a dedicated one-object wrapping key from the attachment root using standard HKDF-SHA256 with fixed domain and unambiguous vault/root/object identifiers. Use BCL HKDF.DeriveKey SHA256 extract+expand with IKM=rootKey32, salt=rootUUID16 big-endian, info=fixed ASCII domain || format u32 big-endian || vault/root/object UUIDs big-endian, output32. Wrap each DEK using a fresh CSPRNG12-byte nonce/tag16; the earlier fixed wrapping nonce proposal is rejected. Every encryption attempt gets a newly generated object UUID and DEK; expose no caller-ID or re-encryption API, and reuse existing objects only as exact ciphertext.

Encrypt each padded64KiB chunk with the object's random key, nonce=8zero bytes || u32 chunk index big-endian (index0..63), and fixed binary AAD binding format/vault/root/object/index/count/originalLength. Each index is encrypted once per fresh DEK; retries or content changes use a new object+DEK. Count=max(1,ceil(length/64KiB)), so empty files use one padded chunk and the empty-file hash. Padding after authenticated original length must be zero and checked. Store authenticated original length and original SHA256 in the encrypted manifest; validate exact ciphertext layout/count, all tags, padding/length and final hash before returning any plaintext. Manifest names/MIME/dimensions are inert metadata; they cannot become paths or automatic resource handles. Check exact encoded/decoded base64 lengths before allocating or decoding. All chunk tags, padding and final SHA256 must pass before returning any plaintext; candidate Open/Inspect/Import also validate complete object content and zero temporary plaintext/keys.

## Snapshot/model and transaction rules
Payload schema5 explicitly adds root identity, immutable object records and note/revision attachment IDs; schema1-4 retain their existing strict rules. Validate unique IDs, complete current/history/trash/image-node references, same-root ownership, immutable byte/hash metadata and whole serialized+envelope budget across every retained object. Retained authenticated unreferenced objects are allowed within the same count/byte limits and are not automatically deleted. Metadata-only edits, duplicate, mode conversion, version restore, batch, hidden recovery, portable transfer and backup must preserve complete objects and references.

Read file bytes boundedly without changing the original; record the original hash. Recheck session/epoch/note membership/source after file/OLE/modal boundaries. Perform bounded encryption synchronously before any async ciphertext-only disk write so key clones do not remain in an I/O worker after lock. Zero owned plaintext/data/wrapping key buffers; document managed UI/image cache limits. Publish a complete preflighted object+note revision atomically. Reject stale or invalid work with unchanged original snapshot; never report saved before current ciphertext commit succeeds.

For the first unit, PDF/Office files are opaque bytes and never parsed or launched. Image decoding/clipboard/drop and explicit open/export UI are later reviewed boundaries. User must be warned before any plaintext export/temp file or external process. Image header/pixel/frame/decode budgets and cache clearing need separate tests before enabling preview.

## Required failing tests before code
- v1/2/3/4 exact original previous migration and flush/replace/process-kill failure invariance
- root anchor failure creates no object/ref; wrong secret, all key-package/chunk mutations, truncation/trailing/duplicate/reused ID and wrong root fail closed
- fresh data keys, nonce uniqueness per object, object immutability, roundtrip original hash/bytes and no plaintext/key/name leakage in current/previous/pending
- whole snapshot/ref/history/size rejection leaves basis/draft/version/events unchanged; nonselected notes and history survive
- duplicate/restore/trash/batch/metadata/mode/hidden recovery and encrypted restart preserve complete object bytes/references
- exact full-backup bytes and independent-root recovery include every referenced object; unsupported old/new formats never overwrite originals
- immediate lock/revoke at file/OLE/modal/async-write boundaries has no late attachment publication or retained live key owner

Independent read-only design review permits only this bounded storage unit when these exact conditions are implemented and tested. Actual diff review remains required. Image/clipboard/drop/open/export boundaries are not included in this initial storage approval. ## Implementation sequence and completion gates
1. Add failing schema5 owned-object/ref/budget fixtures, then typed immutable contracts and strict schema5 JSON/semantic validation. Legacy schemas omit attachment fields when serialized and reject nonempty unsupported attachment state.
2. Add failing cipher roundtrip/tamper/nonce/padding/size/ownership fixtures, then a pure internal bounded object codec. Fixed domains: HKDF info ASCII MEMOAPP-ATTACH-KEK followed by u32BE1 and vault/root/object UUIDs; wrap AAD ASCII MEMOAPP-ATTACH-WRAP followed by u32BE1, the same UUIDs, u64BE original length and u32BE chunk count; chunk AAD ASCII MEMOAPP-ATTACH-CHUNK followed by u32BE1, UUIDs, u32BE index/count and u64BE length. RootUUID16BE is HKDF salt. Wrapped-key record is exactly nonce12+cipher32+tag16; each chunk is cipher65536+tag16 with its derived nonce. Encoded records must be canonical base64 of the exact expected length before allocation.
3. Add failing envelope2/root ownership/mutation/layout/usage fixtures, then version-split envelope parsing/sealing and private root transfer/zeroing. Header MEMOV002/version2/algorithm1 uses existing84-byte field encoding; package offsets84/144/204/280, with lengths60/60/76/(payload+28), exact total308+payload. Envelope1 keeps its original232+payload layout.
4. Add failing durable anchor/fingerprint/flush/replace/stale-lock fixtures, then coordinator-owned explicit root initialization and current commit. Root enablement must not report anchored from preparation/pending; no object encryption before successful current fingerprint. Once a root is committed, root identity cannot be changed/downgraded by ordinary writes. Reject a mismatched hidden-recovery root without discarding its frozen snapshot; an unanchored legacy snapshot with no objects/refs can initialize a fresh root on a later explicit retry.
5. Add failing workspace add/detach/duplicate/history/batch/whole-budget invariance fixtures, then atomically stage object+immutable note references using a new revision. Root keys remain outside the model. Document-only and attachment-reference changes participate in content authority; metadata-only changes do not. All retained ciphertext records stay included in budget and backup even if temporarily unreferenced.
6. Run actual encrypted restart, independent-root full-backup recovery, old-shaped migration/failed migration, crash/lock/hidden recovery and plaintext/key/name scan fixtures plus the complete existing suite. Obtain actual-diff security review before connecting opaque-file import UI; image decode/clipboard/drop/open/export are separate later units. Keep the original134 ledger and final-user/physical-OS acceptance unconfirmed.

Each implementation stage starts with an observed failing synthetic test and ends with the corresponding passing test and full regression evidence. This sequence is inline, with one implementation owner and the existing independent storage reviewer; no main merge, public release or extra authentication/permissions.
