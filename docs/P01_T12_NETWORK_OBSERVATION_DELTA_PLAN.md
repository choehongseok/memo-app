## Existing implementation and evidence

`tests/MemoApp.WindowsChecks/InstalledNetworkObservation.cs` already reads the Windows IP Helper owner-PID TCP and UDP tables for both IPv4 and IPv6. Four SDK layouts are explicit; native returned lengths/counts are checked; each table allocation is capped at 1 MiB and size races get at most three attempts. The positive self-check binds a loopback TCP listener and UDP socket in each supported address family and requires their exact PID/port rows to be observed within two seconds. It logs counts and coverage, not addresses or packet contents. IPv6 unsupported is explicit; IPv6 child tables are still required.

`InstalledPackageChecks.cs` installs/hash-verifies the actual self-contained package in a temporary Unicode path, checks its packaged coreclr module, and launches the production `MemoApp.Windows.exe` twice: default locked and explicit locked tray-start. `ChildMonitor` samples immediately after launch, during startup/GUI-idle waiting and for three seconds idle per launch. Requested interval is 50 ms; successful output includes actual sample count, elapsed/idle time and maximum inter-sample gap. Startup and GUI idle have 30-second/10-second deadlines. Shutdown waits are not network-observed. The untouched installed app creates no vault. The monitor tracks only the installed app PID and checks that it remains alive around each table snapshot; it currently does not bind creation time or discover OCR children.

`.github/workflows/preparation.yml` already builds the fixed OCR bundle, builds the Windows solution, runs Core and isolated cleanup tests, runs WindowsChecks, publishes/packages, then runs `--installed-package`. An earlier WPF failure skips publish/package/installed observation. Cached actual runs `38014327434`, `38016089344`, `38016986323` and `38017598386` have OCR/UI PASS records but no `NETWORK_OBSERVER_SELF_CHECK` or `INSTALLED_CHILD_NETWORK` records; their later package/installed steps were skipped. Thus observer code exists, but those runs do not establish successful installed-startup observation. Earlier OCR proof gates predate that observer. Retain failure history and require fresh actual marker/step evidence before updating feature evidence.

The normal WPF host has an STA entry point and `Application`/dispatcher loop in `Program.cs`; existing focused CLI modes select groups, and `--image-shutdown-worker` proves separate-child execution is already feasible. `MemoApp.WindowsChecks.csproj` is an executable WPF project referencing the actual Windows product project. `OcrProductChecks.cs` exercises the actual `AttachmentPanel` with explicit local model installation/selection and the fixed native engine, exact public Korean/English PNG fixture, read-only OCR preview, explicit encrypted apply, search, reopen and lock. It runs within the test host, not an installed production EXE. `LocalOcrProcess` launches a direct Tesseract child with redirected stdin/stdout/stderr and real completion/settlement; the current observer is never called for that child. PE imports, restricted environment and correct OCR output are separate evidence, not communication observation.

Add one dedicated separate WindowsChecks child that creates actual product WPF controls and a genuine synthetic encrypted session, performs unlocked native editing/search/save, actual local OCR, explicit result apply/search, and lock. Its parent observes that host and each actual fixed Tesseract child using OS snapshots. No production hooks, launch callbacks, backend substitution, engine delay, provider, firewall rule, OS setting, new service or paid SDK.

Evidence has two explicit labels:

1. `installed-production-exe-locked-startup`: existing packaged production executable, existing two scenarios, strengthened identity binding.
2. `test-host-production-wpf-and-native-ocr`: separate WindowsChecks executable/.NET host, actual product MainWindow/AttachmentPanel and local engine, synthetic session. This does not establish installed-EXE unlocked/OCR coverage. Such installed automation is a later independent scope; do not silently relabel the host as the installed app.

A zero-row finding means only that no owned TCP/UDP v4/v6 rows were found in the recorded samples. It is not a firewall test, complete offline proof or a statement about every run.

## Process and observation contract

1. Run the existing positive observer self-check first. Also use a separate synthetic test child with bounded loopback TCP/UDP fixtures to prove cross-process PID+creation filtering; close these before the zero-row app scenario. This is a future explicitly bounded test fixture, not external network access.
2. Preallocate bounded parent output/error drains and observation state before launching the synthetic WPF child. Use redirected local stdio for test-control markers, not network IPC. Child creates its own synthetic recovery secret; keys, note text, image bytes and paths never cross the protocol or enter logs. Only fixed ASCII phase labels, a random run nonce and small counters are allowed; cap each line at 128 bytes, the transcript at 8 KiB and phase transitions at 16. Malformed/duplicate/out-of-order/missing markers fail. Drain actual streams and await actual exit even on failure.
3. Child's ready handshake precedes synthetic actions. Parent obtains the host's creation time and validates exact launched process identity; takes a first snapshot before granting phase start. Capture first-sample delay and coverage start honestly; process launch before the first sample remains an explicit blind interval.
4. Child uses actual MainWindow/SaveCoordinator/native editor/search controls where existing fixtures establish access, an encrypted synthetic note, explicit local model setup and actual AttachmentPanel recognition. Native edit must update the draft, save must succeed, search must find the expected synthetic note, OCR must match the existing independent normalized fixture oracle, explicit encrypted apply must succeed, and lock must release keys/clear sensitive controls. The scenario is not a mock backend and must not weaken any current save/source/lock condition. No browser/file-open links or external models are used.
5. Parent discovers direct descendants of the bound test-host identity via Windows Toolhelp process snapshots, bounded to 4096 total rows and 16 scenario descendants. A candidate must have the expected parent PID, be created after the bound host, and resolve to the exact expected local Tesseract path/manifest SHA verified once with existing fixed length bounds. Check creation time before/after required native table queries. PID reuse, inaccessible required process identity, unknown descendant, ambiguous path or excessive rows/children fail. Do not collect command lines, arbitrary module lists, addresses or packet payloads; report roles/counters only. A process observed after exit does not count as an active sample.
6. Request 50 ms snapshots independently of the WPF dispatcher, covering host startup, unlocked actions, OCR, apply/search and lock. All four tables must succeed for each qualifying sample. Keep measured phase duration, sample count, maximum gap and first/last qualifying timestamps for host and aggregate active samples across discovered bound OCR identities. Aggregate statistics do not claim continuous coverage of each recognition; report discovered identity count and mandatory active sample coverage. Fail on any nonzero owned row. Discovery scans/table calls can overrun the request interval; log actual gaps rather than claiming continuous 50 ms coverage.
7. Require at least one complete active TCP/UDP v4/v6 snapshot of a verified actual Tesseract process during a declared recognition phase. Require host samples for every declared phase and three seconds idle before actions and after lock. Missing OCR-child discovery/active coverage or missed host phase fails; do not treat a quick engine exit as zero network traffic. Use the existing actual fixture and at most two successful recognitions for a fixed bounded coverage opportunity; never add sleeps inside the engine, fake OCR or retry until a desired result. If both finish between scans, report the coverage failure and keep T12 unverified for this delta.
8. Total scenario deadline 60 seconds, ready/startup deadline 10 seconds, each actual OCR operation retains the existing 20-second deadline, and normal child exit/drain deadline 15 seconds. Use one owning finally to terminate only the exact owned test child/tree on failure and await actual exit and stream settlement before releasing observation resources. A cleanup timeout is a failed/incomplete test, not success or evidence that traffic stopped. No UI-thread blocking process wait.

The child phase protocol and OS parent/identity/path observations together determine coverage; a marker alone cannot fabricate an engine sample. Once discovered, continue observing that identity while alive even after recognition completion; a late unexpected engine or child is a failure. If identity disappears between before/after checks, record a lost sample and require another genuinely active sample; bounded deadline/missing coverage still fails.

## Limits and remaining independent work

Socket tables are sampled sequentially, not atomically; they may miss sockets that open/close between samples or before discovery/first sample. UDP rows are bound endpoints, not a packet-transmission detector. Process-owned rows cannot rule out traffic delegated to other processes/services, DNS resolution through OS services, non-TCP/UDP transports, packet contents or later/future actions. Do not collect other processes' endpoints or try to close these limits by changing firewall/OS policy. Build-time SDK/source/model downloads occur outside the observed runtime phases and must remain distinct from runtime communication.

This delta does not establish broad OCR accuracy, CPU/RAM budgets, JPEG/general image support, Android behavior, Microsoft Windows physical offline acceptance, or complete local-only proof. It does establish an independently observed bounded synthetic Windows host/real-engine interval when its mandatory coverage passes. No new user product decision is needed; independent PRE review and root authorization are the next steps.
